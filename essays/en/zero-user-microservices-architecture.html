Zero user, microservices architecture

May 9, 2026 • Software Architecture • 5 min read

Six months ago, I started building ERP software using Go, based on microservices architecture. Initially, I created problems that didn't exist yet then started solving them: “What if I hit 1 million requests per second?”, “What if the system fails during the working day?”, “What if the database crashes?”.

I was fighting with non-existent problems. A month passed while I was working on the API Gateway and User Authentication. I hadn’t even created database tables for inventory. One night, a question came to my mind: “Should I be using Go for this? I don’t have a single user yet”.

After some research, I realized that using Modular Monolith architecture and Python, I could build a reliable system much faster. I merged all services into one monolith, and focusing on business logic suddenly became easy.

Result: I lost a month and a half. I could have spent that time building and releasing an MVP to get my first user and learn their actual requirements.

I finished MVP in four months. In the era of coding agents, spending more time feels like a waste. In a startup, the essential thing is building minimal features, releasing MVP as soon as possible, and testing with real users. Because users say what problems they have and what features are needed for the product.

A founder may think a user needs ten different features, but that theory rarely survives reality. For example, I thought inventory needed batch management. However, the user didn’t touch that feature for 2 months. I deleted it, and nothing changed.

Now I have a rule: First release, then optimize. If a user asks for a specific feature or mentions a specific problem, that is where I focus. Everything else is useless until you have your first ten users.
